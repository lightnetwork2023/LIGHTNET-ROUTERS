# LightNet Q20 firmware notes

- Build: `./build-image.sh` (ImageBuilder at `~/immortalwrt-imagebuilder-23.05.4-ramips-mt7621`, profile `jcg_q20-pb-boot`). Copy factory/sysupgrade to `~/Desktop/asus openwrt/firmware/`.
- Recovery flash: `curl --http0.9 -F firmware=@factory.bin http://192.168.1.1/upload.cgi`, poll `/status.html` until `done`, then GET `/reboot.cgi` (recovery often does not reboot by itself).
- LuCI views: bump the filename (`*-vN.js`) and update `usr/share/luci/menu.d/luci-app-lightnet.json` on every UI change; browsers cache view JS aggressively.
- LuCI's `sysauth_http` cookie has `path=/cgi-bin/luci/`, so it is NOT sent to `/cgi-bin/lightnet-*`. Views send `Authorization: Bearer <L.env.sessionid>`; `lightnet-admin-auth` validates it. uhttpd only forwards standard headers (custom `X-*` headers are dropped).
- Views must set `handleSave/handleSaveApply/handleReset: null` and avoid `: null` children (renders the text "null").
- Adoption policy: wired BATMAN neighbor => auto-adopt; wireless => pending until Approve. Reject stores the satellite's `boot_id` in `/etc/lightnet/rejected/<mac>`; satellite leaves the mesh until reboot (new boot_id clears it).
- UI test: Selenium + `/usr/bin/chromium` + `/usr/bin/chromedriver` (no Node installed, Playwright unusable).
- `build-image.sh` does NOT copy output; copy `bin/targets/ramips/mt7621/*jcg_q20-pb-boot-squashfs-{factory,sysupgrade}.bin` to the Desktop firmware folder manually.
- PB-Boot recovery `info.html` reports board `Xiaomi CR660X` on all Q20 units; flash chip (`F59L1G81MA`/`W29N01HV`/`Unknow`) identifies the unit.
- The PC usually cannot reach satellites directly; SSH via the main: `ssh -o ProxyCommand="ssh -W %h:%p root@192.168.2.1" root@<sat-ip>`. Dropbear has no sftp-server: use `scp -O`.
- If no SSH: log in to LuCI over link-local (`http://[fe80::...%25eth0]/cgi-bin/luci/`) and POST `/cgi-bin/lightnet-role` with `Authorization: Bearer <sysauth>`. ubus `file.exec` is denied.
- Role priority: WAN with a real upstream IP (not 192.168.1/2.x) => root before any controller probing. Unadopted, non-rejected agents with no controller for 90s re-run auto (prevents all-agent deadlock).
- Units: q20-0580 (50:33:f0:a5:05:80), q20-dfac (50:33:f0:44:df:ac, F59L1G81MA), q20-3698 (50:33:f0:5a:36:98, W29N01HV).
- Login: LuCI user `LIGHTNET` (rpcd login section `rpcd.lightnet`), root has the same password (hash set in uci-defaults). Empty root password no longer works. Technician PC SSH uses key `~/.ssh/id_ed25519` (added to live units' `/etc/dropbear/authorized_keys` only, not in the image). Use `-o BatchMode=yes`.
- MT7915 5 GHz AP (phy1-ap0) defaults to the same BSSID `00:0c:43:26:59:97` on every unit; this breaks phones on the mesh. `lightnet-macs ap1` (+7, locally administered) gives each unit its own; set in uci-defaults and `set_base_macs`.
- Satellite names: controller-side aliases in `/etc/lightnet/names/<mac>` (set via `lightnet-adopt` action `rename`), shown as `name` in topology/pending. Shared UI lib is now `lightnet/ui2.js` (rename the file when changing it; LuCI caches it).
- Restart: `lightnet-action` `{"action":"restart","mac":...}`. Main = local reboot; approved satellite = queued in `/tmp/lightnet-cmd/<mac>`, delivered in the next inform response (`"command":"reboot"`, ≤15 s).
- Topology tree (`view/lightnet/topology-v1.js`): satellites report `uplink_mac/iface/tq/signal/rate` (BATMAN next hop toward the controller, from `batctl tg` + `batctl o`); UI maps uplink hardif MACs (+4/+5/+6) back to nodes. Shared UI lib is now `lightnet/ui3.js`.
- Selenium test scripts that click Restart will really reboot units; use view-only scripts for re-checks.
- Cloud enrollment (zero-touch): `lightnet-cloud` (root only) POSTs to `https://lightnetwork.pro/api/router/enroll` signed with HMAC(`/etc/lightnet/enroll.key`); server module `/opt/lightnet_q20.py` (copy in `server/`) auto-provisions under owner 13 via `lightnet_sites.*` → site/nas/WG peer. Provision JSON saved to `/etc/lightnet/server.json`; `lightnet-provision apply` builds `wgln` (WG to 10.0.1.1) + hotspot VLAN; `lightnet-hotspot` runs CoovaChilli on `br-hotspot` (bat0.10) with `net 192.168.88.0/24`, `nasip <wg ip>`, `radiusnasid LIGHTNET`. Chilli option is `nasip` (NOT `radiusnasip`). Satellites join the VLAN when `lightnet-config` returns `hotspot:true`.
- Server key/enroll: `/etc/lightnet-q20/enroll.key` on the VM == `files/etc/lightnet/enroll.key`. Reload Flask with `systemctl reload flask-app` (graceful HUP), never restart during business hours. Backups of app.py in `/opt/backups/q20_*`.
- `firmware.id` is stamped by build-image.sh from git; `sysupgrade.conf` lists specific files so firmware.id/enroll.key/mesh.key always come from the new image. After sysupgrade with kept settings, `/etc/config/lightnet` may lack the `cloud` section — scripts call `ensure_cfg`.
- Sysupgrade -k on satellites has twice left a unit with mesh L2 up but no IP (ROCKY once, GODIAN once); power-cycle / recovery reflash recovers. Root cause not yet found.
- Do NOT join the PC Wi-Fi to the LIGHTNET hotspot for tests (loses upstream Internet); the user tests clients with a phone.
- Portal is router-hosted: chilli's UAM httpd (:3990) serves `wwwdir=/var/run/lightnet-www` under `/www/`; `lightnet-hotspot` copies `files/etc/lightnet/portal/lightnet.html` + writes `config.js` (owner/site/api) there and sets `uamserver http://192.168.88.1:3990/www/lightnet.html?owner=&site=`. The page calls `https://lightnet.lightnetwork.pro/api/buy*` cross-origin (server has CORS, same as the UniFi portal). `uci set lightnet.cloud.portal=server` falls back to the server-hosted `/buy` page. Chilli appends `res=failed|already|logoff`, `uamip`, `uamport`, `mac`, `userurl` to the URL.
- Test the hotspot from the main without Wi-Fi: `ip link add hstest link br-hotspot address 02:aa:bb:cc:dd:01 type macvlan mode bridge; ip link set hstest up; ip addr add 192.168.88.10/24 dev hstest; ip route add 192.168.88.1 dev hstest` then `curl --interface 192.168.88.10 http://192.168.88.1:3990/...` (DHCP replies don't reach the macvlan; chilli still creates the session). A `/logon` with a bad code produces a real Access-Request/Reject on the server (`tcpdump -ni wg0 host 10.0.1.76`). **Do not `ip link del hstest` while chilli runs** — doing so coincided with a kernel reset/reboot of TARIMO (likely macvlan-on-bridge + chilli raw socket). Leave it until the next reboot, or stop chilli first.
- BusyBox `pgrep -x NAME` matches the full argv[0] (`/usr/sbin/chilli`), so `pgrep -x chilli` is always false. Use `lightnet-hotspot running` (pidfile) / `ensure`. This bug made every 5‑min heartbeat restart chilli and drop all client sessions (phones then saw ERR_CONNECTION_REFUSED on :3990 — chilli resets TCP from IPs without a session).
- Billing-bypass guard: after sysupgrade, `uci-defaults` put the main's client SSIDs back on `br-lan` (full Internet, no portal) while satellites stayed on the VLAN. Now `uci-defaults` keeps `network='hotspot'` when `network.hotspot` exists, and `lightnet-hotspot ensure` (boot + every heartbeat) runs `wifi_guard` to move SSIDs back to the VLAN. Check with `ls /sys/class/net/br-hotspot/brif/` (must list `phy0-ap0 phy1-ap0 bat0.10` on the root).
- `br-hotspot` must be in a DROP zone (`hotspot_l2`): the kernel also sees frames to the gateway MAC on the bridge and fw4's default REJECT sent TCP RSTs that raced chilli's SYN-ACK (phones: ERR_CONNECTION_REFUSED on :3990).
- **Never LD_PRELOAD-stub chilli's `dns_copy_res`** (v0.9.2 `libchilli-edns.so`): `dhcp_dns()` checks `if (dlen) return 0` after the record loop, so a stub that does not advance the pointer silently drops ALL client DNS (phones get an IP, no portal, no Internet, log looks clean). The real "dropping malformed DNS" cause is unknown RR types (65 HTTPS/SVCB; type 41 EDNS was already handled in 1.6). Fixed in `packages/coova-chilli/` (1.6-11 = feed 1.6-10 + `patches/040`), built with the ImmortalWrt 23.05.4 SDK at `~/immortalwrt-sdk-23.05.4-ramips-mt7621_gcc-12.3.0_musl.Linux-x86_64` (`./scripts/feeds update packages && ./scripts/feeds install coova-chilli`, copy patch into `feeds/packages/net/coova-chilli/patches/`, bump PKG_RELEASE, disable `CONFIG_PACKAGE_kmod-ipt-coova` in .config — the SDK lacks xtables headers, and the Q20 doesn't use xt_coova). `build-image.sh` copies `packages/*/*.ipk` into the ImageBuilder `packages/` dir so they override the feed.
- Client DNS on the hotspot is answered by the router's dnsmasq (`dhcp.@dnsmasq[0].dns_redirect=1` → fw4 "DNSMASQ HIJACK" redirect :53), not by chilli's `dns1/dns2`; chilli only inspects the packets.
- Emulating a hotspot client from the main with the `hstest` macvlan only works for traffic that really leaves via the bridge; `192.168.88.1` is a local address so curl/ping to it take `lo` and bypass chilli (chilli RSTs connections from IPs without a session → `000`). Use `ip rule add from 192.168.88.250 lookup 100` + `default via 192.168.88.1 dev hstest table 100` and a real remote IP to exercise the dnat path; judge results via `/proc/net/nf_conntrack` (entries with `dport=3990` = redirect worked) and `chilli_query -s /var/run/lightnet-chilli.sock list`. Real phones are still the authoritative test.
- Server: `lightnet_q20.py` no longer calls `reload_freeradius_clients()` (= `systemctl restart freeradius`, fleet-wide auth blip). `clients.conf` has `client lightnet-wg-dynamic { ipaddr=10.0.1.0/24 dynamic_clients=lightnet_dynamic_clients }` backed by `sites-enabled/lightnet-dynamic-clients` (SQL on `nas`); verified 2026-10-04 with a temp `nas` row + `radclient` from 10.0.1.1 → "Adding client 10.0.1.1/32" at runtime. The MikroTik `owner_create_site` path in app.py still restarts; same removal would apply there.
- Releases: tag `vX.Y.Z-cloud` BEFORE `./build-image.sh` and make sure `files/etc/lightnet/firmware.id` is clean (`git checkout -- files/etc/lightnet/firmware.id`), otherwise the version is stamped `-N-g<hash>` / `-dirty`. Publish: `install -o www-data` into `/var/www/lightnetwork/firmware/q20/`, `UPDATE lightnet_firmware_builds SET is_latest=0` + INSERT (url, sha256, allowed=1, is_latest=1), then queue `{"type":"upgrade",...}` in `lightnet_routers.pending_commands` (or use the owner dashboard Upgrade button).
- **hotspot_l2 zone `forward=DROP` is not enough**: fw4 renders zone forward policy as `oifname br-hotspot`, so a client SYN the kernel also sees on br-hotspot (dst MAC = bridge MAC, dst IP on the Internet) falls through to the forward chain's final `handle_reject` → kernel sends a TCP RST spoofed as the remote server, phones get "connection refused" before chilli's 302 (symptom: connected, no Internet, no portal; `tcpdump -ni tun0 tcp port 80` shows `<remote>.80 > phone [R.]` 100 µs after the SYN). Fix = explicit rule `firewall.ln_hs_l2_fwd` (src=hotspot_l2 dest=* target=DROP) in `fw_on`; `wifi_guard` re-applies it on units provisioned by older builds. Verify with `nft list chain inet fw4 forward_hotspot_l2` (counter rising, no RSTs in tcpdump). `tcpdump-mini` is installed on q20-3698 (opkg, not in the image).
- Satellites apply the fleet Wi-Fi profile from `/cgi-bin/lightnet-config` (`config_version` bump → `lightnet-apply-profile`); verified SSID rename LIGHTNET→LIGHTNET2 reached ROCK/GODIAN within one inform cycle.
- **Client DNS dead after boot** (symptom: phones in dnat, `tcpdump -ni tun0 udp port 53` shows `ICMP udp port 53 unreachable`): dnsmasq (bind-dynamic) missed tun0 appearing after it started, so the fw4 DNS hijack to 192.168.88.1:53 hit a closed port. `lightnet-hotspot dns_guard` (after start + every `ensure`) restarts dnsmasq when `netstat -lnu` lacks `<uamlisten>:53`.
- `/etc/nftables.d/90-lightnet-hotspot.nft` drops everything `iifname br-hotspot` at the **raw prerouting** hook: AF_PACKET taps (chilli) already got the frame, the IP stack never does → no kernel RSTs, no duplicate forwarding of established flows out of WAN (before this, every hotspot upstream packet went out twice because `ct state established accept` precedes zone dispatch in fw4's forward chain). The `ln_hs_l2_fwd` rule stays as a fallback. `tcpdump-mini` is now in the image.
- Payment path check: nginx `POST /api/buy` from the router's WAN IP + `buy_payments` row with `provider_ref` = USSD push accepted by AzamPay; `pending`→`paid` depends on the MNO.
- Payment "loads forever, no USSD": server `lightnet_buy.detect_mno()` picks the AzamPay MNO from the phone prefix; 079 (Vodacom), 078 (Airtel), 077 (Yas) were missing → defaulted to Airtel → push went to the wrong wallet, AzamPay still returned a transactionId. Fixed on the server 2026-10-04 (backup `/opt/backups/buy_mno-*`), and `/api/buy` now honours `provider` from the request (`pick_provider`, whitelist Mpesa/Airtel/Tigo/Halopesa/Azampesa); the portal sends the dropdown value. Check a stuck payment with `SELECT phone,provider_ref,status FROM buy_payments WHERE id=…` + the prefix.
- Portal UX: chilli runs with `nouamsuccess`, so `/logon` redirects straight to `userurl` (the `res=success` branch in the page is only a fallback); paid → `location.replace(logonUrl)` immediately, no voucher screen or button. Bump `?v=N` in `lightnet-hotspot` (uamserver) on every portal change — webviews cache hard.
- **Master stays master**: `lightnet-apply-role` (boot/auto) exits early for a root whose `detection` is `wan-upstream|manual|bridge` or whose `lightnet.cloud.status=provisioned` — no WAN check, no mesh probing, no demotion when the uplink has no data. Only `standalone` roots (never had an upstream, no controller found) keep probing/yielding, and the agent-loop yield branch also skips provisioned roots. To demote a master: pick Agent/Auto→reset in the app, or factory reset.
- Satellite upgrade: flash **clean** (`sysupgrade -n`, via `ssh -o ProxyCommand=... root@<sat>`); the controller's `adopted.list` + `names/` make it re-adopt and re-apply SSID/hotspot VLAN by itself (`lightnet-config` → `lightnet-apply-profile`). Kept-settings upgrades are the ones that left units without an IP.
- **Satellite upgrade relay** (`lightnet-satellite-upgrade`): the master publishes the image at `http://192.168.2.1/lightnet-fw.bin` (symlink into `/tmp/lightnet-fw/`), queues `upgrade` in `/tmp/lightnet-cmd/<mac>`; the satellite's `lightnet-inform` fetches it, verifies sha256 + `sysupgrade -T`, then flashes **clean** (`-n`) and re-adopts. `lightnet-cloud` runs `TARGET_BUILD=<fw_build> lightnet-satellite-upgrade stage …` before upgrading the master, so one dashboard Upgrade does the whole site (satellites first, master ~4 min later). Manual: `lightnet-satellite-upgrade url <url> <sha256> [mac…]`, `… status`. Satellites now report their real `firmware` build in informs (and `satellites_json.fw_build` to the server). Satellites on builds older than v0.9.9 ignore the command — flash them once via LuCI (System → Backup/Flash, keep settings OFF) or recovery.
- Clean-flashed satellites lose the technician SSH key (`/etc/dropbear/authorized_keys` is not in the image); manage them through the controller (restart/upgrade/rename) or LuCI.
- **Expiry not enforced until reconnect** (server, fixed 2026-10-05, backup `/opt/backups/radius_remaining-*`): in `sites-enabled/default` the voucher SQL gave the *full* `session_timeout` whenever the match was by username rather than by bound MAC (code re-typed on a second device, or after the phone's private MAC changed). Chilli/MikroTik then kept the session for the whole duration and the disconnect cron could not reach it (it keys on `vouchers.mac_address`). Now `WHEN v.expire_time IS NOT NULL THEN remaining seconds`. Verified with radclient via the dynamic-client path: Session-Timeout 3586 for a voucher with 3586 s left. FreeRADIUS restart needed for policy changes (`freeradius -C` first).
- `sysupgrade -k` output must not be written to the overlay (`/root`): it keeps the flash busy and stage2 fails → reboot without flashing ("Command failed: ubus call system sysupgrade … (Connection failed)" is printed on *success* too, when the SSH session is killed). Site power flaps also cause reboot bursts — check `uptime` on all three before blaming an upgrade.
- **Master Wi-Fi off after a kept-settings upgrade**: `uci-defaults` always rewrites `default_radio0/1` (disabled=1, ssid LIGHTNET) and the sticky-root boot path skips `apply_root`, so the master radiated nothing (satellites were fine). Now the sticky branch calls `apply_client_wifi`, and `lightnet-hotspot wifi_guard` also enforces fleet ssid + disabled=0 on a provisioned root (self-heals every heartbeat). Check with `iw dev` on the master: `phy0-ap0`/`phy1-ap0` must exist with the fleet SSID.
- **Role lock stuck forever**: `lightnet-apply-role` holds `flock` on fd 9 (`/tmp/lightnet-role.lock`); `lightnet-hotspot start` spawned chilli from inside it, chilli inherited fd 9, and every later `lightnet-apply-role apply-wifi` (the app's Wi-Fi save on the master) logged "role change skipped; another detector is running" and did nothing. Chilli and the background `ensure` are now started with `9>&-`. Find a lock holder with `for p in /proc/[0-9]*; do ls -l $p/fd | grep -q role.lock && cat $p/cmdline; done`.
- Hotspot clients cannot open LuCI/`192.168.2.1`: the `hotspot` zone (tun0) has `input=REJECT` and only allows 3990/3991, DNS and ICMP, and unauthenticated clients are redirected by chilli anyway. Wired ports today: master `lan1` → br-lan (management, Internet without portal), `lan2` → BATMAN backhaul; satellite `lan1`+`lan2` → br-lan (Internet without portal), `wan` → BATMAN. Only the Wi-Fi SSIDs sit on the chilli VLAN.
- **All client ports are portal ports** (v0.9.11): `lightnet-hotspot net on` → `pin_ports` moves master `lan1` / satellite `lan1`+`lan2` from br-lan into br-hotspot (backhaul ports master `lan2` / satellite `wan` stay BATMAN hardifs); `wifi_guard` re-pins on the root every heartbeat, `apply_root`/`apply_agent` re-pin after a role re-apply, `net off` gives them back. Authenticated hotspot clients may reach the router on tcp 22/80/443 (`firewall.ln_hs_mgmt`), so management = plug/connect → enter a voucher (or be MAC-bound) → `http://192.168.2.1`. **Technician PC on the master's lan1 therefore needs a voucher first**: add `192.168.88.10/24` to eth0 + route `192.168.2.1/32 via 192.168.88.1`, `curl "http://192.168.88.1:3990/logon?username=<voucher>&password=ROCKY221122"`, then `ssh -b 192.168.88.10 root@192.168.2.1`. The PC MAC `18:db:f2:14:17:a2` is MAC-bound to voucher `1065248160` until 2026-11-30, so it currently passes without typing anything. `br-lan` on the master now only has `bat0` (satellite management over the mesh).
- Backgrounding a script over ssh: redirect stdin too (`sh x.sh >/dev/null 2>&1 </dev/null &`), otherwise it dies with the session (the first port-switch attempt silently never ran).
- Kept-settings upgrade of a master on v0.9.11: radios came up before the sticky-root path restored the wifi-ifaces, so the config was right but no `phy*-ap0` existed. The sticky branch now runs `wifi reload` after `apply_client_wifi`, and `wifi_guard` reloads wifi when `/sys/class/net/phy0-ap0`/`phy1-ap0` are both missing on a provisioned root (log: "client APs missing; reloading wifi").
- **Device identity is pinned to the factory label MAC** (v0.9.13): `lightnet-macs id` reads the DT `label-mac-device` (gmac0, Factory NVMEM `0x3fff4`) via `get_mac_label`, pins it in `/etc/lightnet/device.mac` (kept by sysupgrade.conf), and rejects locally administered `02:` MACs in the sysfs fallback (eth0 → lan1 → wan). Before this the ID came from `/sys/class/net/lan1|wan|eth0/address`; when `lan1` was not yet resolved the ID became the rewritten `02:…+4` WAN MAC after a reboot, so the controller saw a "new" satellite asking to be adopted (MESHED 02 incident, 2026-10-06). lan1 == eth0 == label MAC on DSA, so existing fleet IDs do not change.
- **Main `lan1` = wired management port, no voucher** (v0.9.14): on the root, `lightnet-hotspot pin_ports` moves `lan1` into `br-mgmt` (`network.mgmt` 192.168.200.1/24, `dhcp.mgmt` with `dhcp_option` `3` (no router), `121,192.168.2.1/32,192.168.200.1`, `6,192.168.200.1`) and firewall zone `mgmt` (input REJECT + rules tcp 22/80/443, udp 53/67/68, icmp; forward REJECT → no Internet bypass). Satellites keep `lan1`+`lan2` on the portal bridge; Wi-Fi everywhere stays behind chilli (`ln_hs_mgmt` after voucher). `wifi_guard` re-applies it every heartbeat (also on units upgraded with kept settings), `net off` removes it. Live-verified on GODIAN 2026-10-07 (PC got 192.168.200.148, LuCI via 192.168.2.1, `curl --interface <mgmt ip> 1.1.1.1` blocked, chilli sessions untouched).
- Technician PC (NetworkManager): "Wired connection 1" is now plain DHCP + `ipv4.never-default yes`, `ipv4.ignore-auto-dns yes`, `ipv4.dhcp-timeout infinity` (so the Wi-Fi stays the Internet route). The old static recovery IPs (192.168.1.10/.2, 192.168.0.2 + 192.168.1.1/32 route) live in a separate, non-autoconnect profile **"Q20 Recovery"** — they conflicted with home Wi-Fi networks on 192.168.1.0/24 (DNS to 192.168.1.1 went out eth0 → "we lose data when the PC is plugged into the main"). `nmcli con up "Q20 Recovery"` for PB-Boot flashing. - **All client ports on the voucher system; wired = management without voucher** (v0.9.15, replaces the v0.9.14 br-mgmt idea): root `lan1` is back in `br-hotspot`; satellites put `lan1`+`lan2` in `br-hswired` = `bat0.11` (wired VLAN) which the root adds to `br-hotspot`, so the root can tell wired from Wi-Fi. `ruleset-post/lightnet-bridge.nft` (`table bridge lightnet`, needs `kmod-nft-bridge`) marks frames from `{lan1, bat0.11}` with `0x4c`; `90-lightnet-hotspot.nft` does `update @ln_wired { ip saddr }` before the raw drop; `chain-pre/input_hotspot/lightnet-mgmt.nft` accepts tcp 22/80/443 from `@ln_wired` or `@ln_authed`, else `reject with tcp reset`. chilli conf gets `uamallowed 192.168.2.1` + `conup/condown /usr/sbin/lightnet-chilli-con{up,down}` (→ `lightnet-chilli-hook`, keeps `ln_authed`); `lightnet-hotspot sync-authed` rebuilds the set from `chilli_query list` after fw4 reloads (every `ensure`). `ln_hs_mgmt` and all `ln_mgmt_*` uci sections are deleted (`mgmt_cleanup`).
